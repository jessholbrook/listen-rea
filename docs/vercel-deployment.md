## Enable the research workspace

Configure these in the new project's **Settings → Environment Variables**, scoped to the intended deployment environment:

| Setting                                  | Purpose                                                                                                                                                                                                                       |
| ---------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `TURSO_DATABASE_URL`, `TURSO_AUTH_TOKEN` | Supplied by the connected Turso marketplace resource. The app also supports `LIBSQL_URL` / `LIBSQL_AUTH_TOKEN` for manual configuration; that pair takes precedence. Hosted database URLs must use `libsql://` or `https://`. |
| `BLOB_READ_WRITE_TOKEN`                  | Token for a **private** Vercel Blob store attached to the project. Alternatively configure the SDK's OIDC access with `BLOB_STORE_ID`.                                                                                        |
| `RESEARCH_SETUP_CODE`                    | A private random code of at least 16 characters, used only when creating the first owner. Generate and enter it securely.                                                                                                     |
| `RESEARCH_AI_KEY`                        | Optional for manual workflows; required for AI drafting, probing, synthesis and provider speech. Enter your actual OpenAI API key securely in Vercel.                                                                         |

The cloud development environment's injected provider credential is bound to its own proxy. **Do not copy that injected value into Vercel.** Vercel needs its own provider credential. Never put keys, tokens or the setup code into chat, source control or CLI command arguments.

Redeploy after adding configuration. The home-page mode is selected during the build. Create the first account with the setup code, then invite teammates from **Team & settings**. Subsequent public signup is disabled; invitations are scoped, expiring and single-use. Separate preview and production databases/stores to prevent test interviews affecting real research.

## Local prebuilt deployment

A local Vercel build is also supported with `vercel build --prod` followed by `npm run prepare:vercel` and `vercel deploy --prebuilt --prod`. Pull Production settings/environment first (`vercel pull --environment production`), keep `.vercel/.env.production.local` private, and retain it until the build finishes. The home-page workspace/demo mode depends on database configuration **at build time**. Secret values that Vercel replaces with `[SENSITIVE]` are placeholders; do not replace them with this cloud environment's injected AI credential. Runtime secrets continue to come from the Vercel project configuration.

`next.config.ts` explicitly excludes `.data`, `.env*`, `test-results` and `.vercel` from server file tracing. The Vercel builder also adds dotenv entries directly to its generated `filePathMap`; `npm run prepare:vercel` removes those local-only references without changing source files or runtime assets. Keep that packaging step, the tracing exclusions and `.vercelignore`; local databases, environment files and downloaded test media are not runtime dependencies. A prebuilt upload must have no warning about excluded required files: dangling traced links can cause deployment to fail with ENOENT. Before uploading, verify the API trace still contains `ffmpeg-static/ffmpeg` and `assets/DejaVuSans.ttf`, the output contains no local private files, and the generated home page selects the research workspace. Do not externalize PptxGenJS. The compiled-server Pulse and reporting/media checks exercise the resulting production build.

A prebuilt deployment still goes through Vercel initialization and can wait in the platform's system build queue. Keep one current pending release rather than repeatedly submitting identical builds. Check actual deployment status before claiming it is live; an npm dist-tags warning from the CLI's update worker is not authoritative deployment status.
