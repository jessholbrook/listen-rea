# Follow-up activity history

Open **Research library → Action center → Follow-up activity history**, or choose **View task history** on a follow-up. Current workspace members, including readers, can inspect the history. English, Spanish and French controls are available.

Successful task creation, individual edits and operations-triage changes record their actor, timestamp, task version and before/after assignment, due date and status. A title edit records only a title-change flag; previous title text is not retained. Automatic clearing of a departed assignee records an automatic actor. No-op saves, idempotent creation retries, stale/conflicting writes, previewing, and stable reads do not create user events. Recording and the owning task mutation share a transaction: an event-write failure rolls back the task change. Triage records events only for independently successful changed rows.

New activity is recorded from this release onward. Existing tasks receive no invented creation event or backfilled history; their next actual change starts their record. Up to **100 recent events per task** are retained, with an additional 200,000-character record bound and an omitted count. Sequence numbers keep increasing when older events are trimmed. This is recent coordination history, not a permanent audit trail.

Filters intersect collection, exact task, person involved (actor or before/after assignee), action, changed field and inclusive calendar dates. Automatic validation is a person-filter option. Actions distinguish creation, individual edits, triage and unavailable-assignee cleanup. Assignment, due date, status and title can be filtered independently. Creation counts as setting its non-empty values/status, rather than changing a title. Dates default to the viewer’s browser time zone. Reporting controls can explicitly choose another time zone for activity filters and files; saved reporting views preserve that choice. Pages contain 20 events, newest first, with deterministic task/sequence/event-ID tie breaks. The omitted count describes older events outside retention for the selected task/collection, independently of other filters.

Display responses resolve only current task/collection titles and current member names. All events for a renamed task show its current title; members who leave the workspace display as unavailable. Restoring a member does not restore their cleared assignment. Stored records contain coordination IDs, dates, status codes, counters and a title-change flag only: no copied titles, member names, research excerpts, source labels/links, comments, original creation hashes, email addresses or provider output.

**Open current task** reloads the original task from the current workspace queue before opening its editor. Readers receive a focused read-only task row. Completed tasks remain reachable. The destination selects the current task’s collection and title with all statuses; it never opens a replacement ID. Removed or unavailable tasks show an unavailable message. History filters are retained when returning from task editing. History and triage navigation are guarded while an editor or triage draft is open. Failed or superseded reads clear prior history; requests are aborted on navigation and old responses cannot overwrite newer filters. Unavailable selected task/collection/person IDs remain explicit instead of silently widening the scope.

Task deletion removes its complete history. Linked research withdrawal, source deletion or collection removal erases the dependent task and history through the original dependency cleanup. General collection tasks retain their history while that collection remains valid; tasks should be linked to research when source-based erasure is intended. Orphan history records are pruned when the original task is absent. A new task ID starts a new history. Workspace cleanup removes all owned records. There is no retained deletion event or public/shared-report history access.

`GET library/task-activity` is authenticated, current-workspace-scoped and read-only. It strictly validates UUIDs, action and changed-field enums, ordered real dates, time zone, bounded page number, duplicate and unknown parameters. Mutation methods are rejected. Individual task mutation permissions are rechecked against current membership/role inside the task transaction; changing roles after authentication cannot manufacture an attributed edit.

No new service, migration, environment variable, provider call, domain or email setup is required. Normal task/handoff review and export rules remain in force. Seven dedicated API/unit cases cover attribution, retries/no-ops/conflicts, minimal storage, individual/triage/automatic paths, current and masked names, authentication/workspace/reader boundaries, strict filters, local-calendar boundaries, retention/pagination, no backfill, dependency/orphan erasure, concurrency and rollback on event failure. Mobile browser checks cover all three languages, filter intersections, task edit/read-only navigation, retained filters, local leap-day dates, pagination, current/departed people and erasure.
