# Recruitment and payout integration plan

Reviewed October 29, 2026 · America/Los_Angeles · Internal Echo Lab workspace

**Recommendation: build Prolific recruitment first, then add Tremendous for participants recruited outside Prolific.** Prolific supplies the panel and handles its participants’ compensation. Tremendous supplies payouts, not recruitment. Paying Prolific participants through both systems would risk duplicate compensation.

Jess confirmed there are no panel/payout accounts yet and chose automation first. Reviewed REST/MCP study automation is now merged and live. This document compares public provider documentation and proposes the next engineering milestone; no provider account was created, application submitted, participant contacted or payment made. Human pilot and domain-dependent email remain deferred.

Tremendous’s link option removes the need for **Echo Lab to send reward email from a verified custom domain**. It does not remove provider account/identity requirements, possible recipient contact requirements, or the need for a secure way for the participant to return and claim a reviewed reward. Existing Echo Lab invitation email remains deferred.

## Illustrative cost, not an approved budget

For **10 completed, 15-minute sessions at $12/hour**: participant rewards are $30; a 42.8% Prolific corporate fee adds $12.84, for **$42.84 before tax and adjustments**. This is arithmetic using the public fee, not a vendor quote. Screen-out compensation, extra time/pay adjustments, replacements, audience pricing and tax can change the total. Confirm the account’s currency and current quote before any paid launch. Do not treat Echo Lab’s existing incentive ledger as an authoritative provider balance.

Ten $10 Tremendous gift-card rewards would have a $100 face value; the documented lack of platform fees does not guarantee a $100 total for every product, country, payout method or funding source. Prolific participants should not also receive the ordinary study reward through Tremendous.

## Next milestone: Prolific connector with paid launch disabled by default

Build participant handoff, provider draft management, explicit budget/launch controls and submission reconciliation as one substantial workflow. We can build and verify local fixtures before Jess opens an account. A configured account is needed to validate vendor behavior; real recruitment is a later explicit action.

### 1. Connection and reviewed provider draft

Add an admin-only Prolific connection using a deployment secret and a verified vendor account/workspace identity. Credentials stay server-side. Scope this first version to our one internal workspace; do not offer multi-customer SaaS account delegation.

Bind one Prolific study to one published Echo Lab revision. The review screen shows audience filters, device/microphone requirements, estimated duration, reward/currency, places, screening/withdrawal terms and a current provider cost estimate. Use the existing study/editor, fielding, handoff and background infrastructure; keep provider configuration separate from ordinary guide changes.

Create/update an **unpublished** vendor draft only after the reviewed configuration is current. Capture the vendor draft ID, request/body hash and operation state. The public docs establish study creation support but do not establish a general idempotency guarantee for every mutating endpoint. After an ambiguous write, reconcile using saved operation/provider identifiers; never silently create another study or republish it with a new request ID.

### 2. Participant admission and return

Extend the existing handoff/provider namespace with Prolific rather than overloading Qualtrics, Rally or general participant tags. Its documented URL placeholders are `{{%PROLIFIC_PID%}}`, `{{%STUDY_ID%}}` and `{{%SESSION_ID%}}`. Bind these to the configured vendor study and Echo Lab revision, validate bounded opaque identifiers, retain the existing consent/admission/recovery behavior and reject conflicting provider parameters.

URL values are claims, not verified identities or proof of payment. Reconcile them against the authenticated provider submission API before compensation decisions. Repeated opens/retries must recover one interview without creating another paid participant. Account for Echo Lab admission limits and provider places independently; pauses block new admissions while preserving existing-session recovery.

Generate terminal destinations only from reviewed provider completion-code settings. Distinguish completed, screened-out, returned/withdrawn, timed-out and technical-failure paths. A return-link click or an Echo Lab completion is not a settlement receipt. Keep completion-code actions in manual-review mode for the first connector; never copy the documentation’s automatic-approval example into our default configuration. [P5–P7]

### 3. Test mode, budget and launch

The API testing reference documents **no-credit test participants and `/studies/{id}/test-study`**. A separate setup guide still calls the participant-test feature limited beta. Confirm access on Jess’s account before promising hosted no-cost end-to-end tests. If it is unavailable, use local contract fixtures and request vendor access; do not substitute a paid ordinary study. [P3–P4]

Keep test and production operation records distinct even though these testing endpoints use the regular Prolific API host. Do not describe Prolific as offering Tremendous’s separate sandbox host.

Production launch requires a current, explicitly reviewed provider configuration and total cost cap, a funded account and a separate admin launch decision. Opening ordinary Echo Lab fielding or applying an existing MCP fielding request must not publish a paid vendor study. The reviewed automation tools retain their current scope; no paid launch/bonus/approval tool is added to bearer clients in this milestone.

Coordinate Echo Lab and provider states explicitly. If one side pauses/closes and the other fails, show the mismatch and stop further local admissions while reconciliation continues. Do not claim this can instantly stop provider-side liabilities already incurred. Never increase places, replace returned/rejected submissions or raise rewards automatically outside the approved allocation. Public documentation says some returns/rejections can reopen places on an active study. [P6]

### 4. Submission review, compensation and reconciliation

Add a provider roster matching vendor submissions to Echo Lab interviews, with independent **research inclusion**, **compensation decision**, **provider state** and **payment reconciliation**. The current `incentiveEligibility` only permits completed, included native responses; it cannot represent every provider obligation. Do not use source exclusion, withdrawal or our ordinary screening rule as an automatic payment rejection. Implement provider-specific screening/partial-pay rules only after their contract is verified. Prolific’s study model includes custom screening with fixed rewards. [P5]

Show the approved amount and provider status before an admin approves a submission or bonus. An approval is a real compensation action. Initially keep rejection/bonus actions in the provider dashboard, with read-only reconciliation in Echo Lab, until provider rules and repeat-request behavior are validated. In-app approval can follow as a separately reviewed paid-operation scope.

Prolific documents automatic approval after **21 days awaiting review**, even when we intend to review manually. Display provider deadlines, alert the team before them and reconcile externally approved submissions. Our local pending state does not prevent the provider’s automatic payment. [P6]

Use signed webhooks plus queued processing and periodic/manual reconciliation. Prolific documents HMAC verification with `X-Prolific-Request-Signature` and `X-Prolific-Request-Timestamp`; add replay/event deduplication using the documented event contract. Verify raw-body signing against provider fixtures, re-fetch authoritative records as needed and tolerate duplicates/out-of-order events. Webhook delivery to Vercel must work without leaking a deployment-protection bypass secret into participant links; confirm the project’s public access policy before accepting real recruits. [P8]

### 5. Acceptance criteria

The connector is ready for review when:

- Unconfigured and test-only modes cannot publish a paid study; ordinary fielding/API/MCP actions cannot cross that boundary.
- A reviewed vendor draft and exact Echo Lab revision stay bound; stale guide, scope, fee, currency, audience, capacity or permission changes invalidate launch approval.
- Admission/return handles all three Prolific identifiers, wrong studies, forged claims, duplicate/lost retries, pause/resume, screen-out/withdrawal and existing handoff compatibility.
- Provider actions survive ambiguous failures without duplicate study creation, launch or compensation. Cost caps include fees and any explicitly supported adjustments; no automatic budget increase or currency conversion occurs.
- Roster and reconciliation distinguish app completion, source exclusion, provider approval and payment. Deadline/auto-approval behavior, returned/rejected-place replacement and webhook replay/order are covered by independent fixtures.
- Source erasure deletes local research/identifier copies and cancels unsent actions. A minimal opaque spent-operation record prevents replay. External provider financial records/payments are not represented as erased or reversed by an Echo Lab deletion; decide the financial-record retention contract before enabling real compensation writes.
- Local contract/HTTP/browser checks and existing recruitment/incentive/handoff/API/OAuth regressions pass; actual provider testing is labeled separately from fixtures. Preserve the paused pilot and existing accounts during hosted checks.

## Following milestone: Tremendous reward links for our own participants

Use a separate sandbox account and key at `testflight.tremendous.com`; sandbox and production share no data. The documentation supplies simulated funds and separate key prefixes. A sandbox redemption does not prove every production product’s external fulfillment. Production access requires its separate review; no live account/funding is assumed. [T1–T3]

Extend the current frozen incentive approval rather than treating a manual ledger entry as a money-transfer API call. Initial scope: USD only, one reward per current approved obligation, admin-confirmed product/funding source/total, and provider-backed reconciliation. Keep manual-payment recording distinct from provider-executed orders.

Use a durable opaque `external_id` for every order. Tremendous documents equivalent repeated requests returning the same order with **201**, changed parameters returning **409**, and no new charge while a card outcome remains unknown. Preserve that reference across ambiguous failures and source erasure; a new random request must never become an accidental second payout. [T4]

Use `LINK` delivery and a token-authorized participant claim page after reward approval. Keep contact information, if required by the actual provider contract, separate from research text and collect it with explicit consent. Never place redeemable links in the incentive ledger, CSV, API/MCP results, routine logs or shared reports. Generate a link only on an authorized claim read and avoid storing it; if short-lived encrypted storage is unavoidable, specify its retention separately. Tremendous says an existing reward GET does not return its original link and a newly generated link **does not invalidate previous links**. Hiding a claim page, deleting a response or regenerating a link therefore does not revoke an already disclosed reward. [T5]

Track order/funding state, reward availability, delivery and redemption separately. Successful link generation or an `EXECUTED` order is not proof the recipient has redeemed a specific product. Verify signed Tremendous webhooks using its raw-body HMAC contract and deduplicate event UUIDs; reconcile missed events through provider reads. Avoid automatic reissue or refunds based only on delivery errors. [T6]

Acceptance: sandbox-only defaults; exact and concurrent retries; insufficient funds; pending/failed/unknown outcomes; changed approval/source/role; unauthorized/erased claims; link exposure prevention; duplicate/out-of-order webhooks; and accurate reconciliation/export. Agree on financial retention and treatment of earned compensation before turning on production payouts, since the existing ledger currently erases its records with the source.

For the proposed Prolific build, no key is needed to implement local fixtures. For actual provider testing Jess will need a researcher account, API token and confirmation that no-credit testing is enabled.
