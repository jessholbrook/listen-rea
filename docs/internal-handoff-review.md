# Internal handoff review

Open **Research library → Collections → Open review dashboard → Internal handoff review** below a saved handoff packet. Request up to ten current workspace editors, add comments, resolve feedback and collect each requested person's approval before the separate final packet approval and text/CSV export. English, Spanish and French interfaces are available. Everything stays inside Echo Lab; this workflow requires no email provider or domain.

Reviewer requests are optional. A packet with no requested reviewers and no open comments retains its existing final-review workflow. Editors can change the reviewer list, including requesting themselves for a one-person workspace. This is team coordination, not an enforced organizational approval policy. Removing reviewers is an explicit configuration change that clears final approval.

## Review behavior

Each requested person approves or withdraws only their own decision. All requested reviewers must approve the current eligible packet and all comments must be resolved before final approval. Completing internal review does not itself approve export: read the current preview, check the final attestation and approve the packet separately. These actions never approve the underlying findings, transcripts or briefs, or complete follow-up tasks.

Changes to packet content or its research/task context reset reviewer decisions. Adding or reopening a comment, deleting a comment, or changing reviewers also resets decisions. Reviewer-list, comment and decision changes clear existing final packet approval. [Due-date changes](review-planning-deadlines.md) preserve content decisions and final approval because they only schedule work. Resolving comments preserves any still-current decisions. A reviewer who leaves the workspace or loses edit access remains visibly unavailable and blocks final approval until the reviewer list is changed; returning does not restore an old vote.

Workspace readers can view feedback. Editors can comment and resolve/reopen any comment; only its author or an administrator can delete it. Comments are plain text, up to 2,000 characters each, with a lifetime limit of 100 comments per packet. Deletion does not restore that allowance. Deleted comment requests retain content-free hashes so retries cannot resurrect their text. Current display names are resolved from workspace membership; former members use a neutral placeholder. Private comments and reviewer decisions are excluded from packet text/CSV downloads.

Save reviewer selections or comments before editing packet content. Unsaved packet changes block feedback actions; unsaved feedback blocks packet edits and export. Refreshing reloads saved state and discards unsaved text. Other sessions' changes are checked again on the server; conflicts require refreshing before continuing.

## Lifecycle and access

Feedback belongs to the current packet generation. Whole-packet deletion, collection deletion or removal of captured source/answer/brief/task dependencies erases its comments, decisions and comment tombstones with the packet. Context added after initial drafting is captured when feedback is saved, so comments discussing that context are removed with it. Orphan feedback is pruned during collection handoff cleanup. Old generation IDs cannot write into a replacement packet. The record stores the current discussion and decisions, not an immutable approval audit history.

`POST /api/library/collections/:collectionId/handoff/feedback` accepts strict operations with common `{id,packetVersion,version,signature}` fields. Core discussion operations are `assign` with unique `reviewerIds`, `comment` with `requestId` and `body`, `resolve` with `commentId` and `resolved`, `decision` with `approved`, and `delete_comment` with `commentId`. The server binds decisions to the authenticated person and current content signature, rejects stale/future/foreign writes, serializes concurrent mutations and supports exact comment/decision retries. Stored request hashes, author IDs, dependency arrays and decision signatures are excluded from feedback views. Only existing workspace editor roles can mutate feedback.
