# Team review workload planning

Open **Research library → Review inbox → Team workload** for current pending and overdue review load by person. English, Spanish and French controls are available. Counts describe requests, not study size, hours or personal capacity. No workload snapshots, new coordination records, email, domains or provider calls are involved.

## Overview and review navigation

The overview starts with everyone, including current editors with no requests and unavailable people who still have scoped review requests. Filter by collection, packet/collection title and everyone/pending/overdue load. Each card shows pending, overdue, due-today, next-seven-days, undated, blocked-pending and approved-current decision counts, plus its earliest pending deadline. A packet requested from two people counts once for each person. Approved reviews do not become overdue. Blocked counts include pending requests on blocked packets and unavailable pending reviewers. Existing local-calendar deadline rules apply; counts update on local-day changes, window focus and refreshed data.

Cards sort by descending overdue count, descending pending count, earliest pending deadline, name and ID. Counts are scoped to the overview's collection/title filters. **Show pending requests** opens that person's original packet requests, ordered by date, blocked status and ID. Both member cards and request lists use 20-row pagination. **Open handoff packet** opens the current original editor; closing it refreshes workload data. The overview filters and selected person survive refresh and packet navigation. A removed collection retains an unavailable filter; a removed selected person stays an explicit unavailable/empty selection. The view does not silently widen either scope.

## Reassignment

Existing editors can select **Reassign review request** on a pending request. The app prepares the current packet generation and review version, shows the source person/date and eligible replacements, and requires acknowledgement before confirmation. The replacement must be a current workspace editor who is not already requested on that packet. Choices show workspace-wide pending/overdue totals from the last inbox refresh, even when the overview is filtered. They are planning information, not a capacity limit or automatic recommendation.

Confirming moves exactly one requested reviewer and transfers that person's due date. Other reviewer dates and private comments remain. It resets all current reviewer decisions and final packet approval, matching existing reviewer-list change rules. The replacement must submit their own decision; the former reviewer loses decision access for that request. Explicit current final approval remains required for export. Reassignment never approves sources/findings/briefs or completes research tasks.

Completed current review decisions cannot be reassigned here. Changes to the full reviewer list remain available in the original packet editor. Existing requested people cannot be merged into a smaller quorum through reassignment. Unavailable pending reviewers can be replaced by an eligible editor, carrying their original date; returning to the workspace does not undo the transfer. If no eligible replacement exists, the form explains the restriction. Cancelling makes no change.

While preparing or editing a reassignment, adjacent workload filters, navigation, refresh and other requests are disabled. A cancel action remains available before submission. Opening a packet closes the workload editor. Fresh source/assignment/date/member changes are checked again transactionally on confirmation. Conflicts or lost permissions clear the displayed queue/form until refresh; old plans are never retried automatically. An exact repeat of an already-applied reassignment returns a conflict, so refresh to inspect the current result after an uncertain network response.

## API, access and lifecycle

`GET /api/library/collections/:collectionId/handoff/planning?id=:packetId` is editor-only and generation-scoped. It returns the current packet ID/title/version, feedback version, content signature, current reviewers/dates/decisions and editable member ID/name choices. It returns no packet summary/preview, finding or transcript text, comment bodies/history, emails, workspace IDs or request hashes. Unsupported methods return 405, strict-query errors 400, missing/foreign/generation mismatches 404, and read-only users 403. Normal inbox reads include an edit-capability flag; workspace readers can view workload counts and open read-only packets but cannot prepare or perform reassignment.

`POST .../handoff/feedback` accepts strict operation `{op:"reassign",id,packetVersion,version,signature,fromReviewerId,toReviewerId}`. The source must still be requested and pending; the target must remain an editable workspace member outside the current requested list. The IDs must differ. Existing version/signature/workspace/generation checks apply; divergent concurrent plans cannot replace the same request twice. All changes occur in the original feedback transaction with packet approval invalidation. No copied labels, workload documents, reassignment history records or new request-replay stores are created.

Source/collection/packet deletion and orphan pruning erase the original records, dates and comments, removing workload inputs on refresh. Old preparation links and assignment plans cannot resurrect a deleted packet or address a replacement generation. Aggregation reads the same current minimal inbox projection used by review requests, including existing research/task/feedback revalidation and erasure rules.
