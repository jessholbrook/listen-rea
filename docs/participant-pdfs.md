# Private PDF participant attachments

Enable **Allow optional participant PDF attachment** on an open-ended question, save and publish. The flag is off by default and frozen with the admitted interview’s guide. Participants may continue without a PDF, or share one PDF with that answer after entering a description and checking the separate sharing consent. An image and a PDF can be attached independently when both are enabled.

Participant controls and PDF viewing are available in English, Spanish and French. A saved draft survives reload; upload/answer retries bind the exact file and description to the same admitted session and turn version. Changing bytes or description requires a new upload attempt. The selected file is not uploaded until **Upload PDF** is chosen. The answer must include its saved draft PDF ID or the participant must remove that draft. Submitted files can be erased by the research team.

Limits: 3 MB for input and prepared output, 1–20 pages, at most 5,000 indirect objects and page dimensions up to 14,400 points per side. Encrypted PDFs and documents with AcroForm fields are rejected. A separate Node parser process has an eight-second deadline and a 96 MB V8 old-space limit. The process receives file bytes, not application credentials. These are resource bounds, not a malware-scanning guarantee.

Preparation copies static page content into a new PDF. Original document title/author and document-level actions are not copied; page annotations, additional actions and page metadata are removed. Output preparation is deterministic so a lost storage acknowledgement can adopt only identical prepared bytes on retry. This does not remove personal information printed on a page or necessarily metadata inside embedded resources. Participants are asked to remove personal details before sharing.

The private viewer fetches the prepared PDF through an authorized application route and renders one page at a time on a canvas. It uses locally hosted, versioned PDF.js worker/font/CMap/Wasm assets, with no annotation/action layer, no XFA forms, bounded images/canvas size and loading/render deadlines. It does not use a native PDF iframe or send documents to an external viewer. **Download PDF** saves the prepared copy. File responses, including byte ranges and generic recording aliases, use private/no-store headers, attachment disposition, `nosniff` and a sandboxed document policy.

Participant file access requires the original interview token and matching media row; researcher access requires the source study’s workspace session. Cross-session/workspace and anonymous requests are denied. Files use private Blob storage when hosted and the existing protected local storage adapter during development. Original filenames are not retained. Descriptions are limited to 500 characters, and an interview can retain at most 20 PDF attachments.

In **Responses → participant transcript**, the team can view pages, save a PDF quality judgment (usable, unclear/unreadable, irrelevant, privacy concern or uncertain), and write internal notes. Reviews start unreviewed, record authenticated attribution/time, and preserve up to 200 revisions. Optimistic versions prevent an editor from overwriting another review. **Reload saved PDF review** explicitly discards local edits. Reviews bind to the source file digest, saved PDF metadata, answer and prompt. A draft PDF cannot be reviewed until submitted with its answer.

PDF review notes and history are separate from participant payloads. The latest notes/corrections can enter [separate analysis/report appendices](pdf-observations.md) through explicit inclusion; [PDF observation synthesis](pdf-observation-synthesis.md) is a separate explicit AI request. Private history remains internal. [PDF text extraction with page citations and researcher verification](pdf-text.md) is now implemented as a separate internal workflow. [AI synthesis of explicitly included, verified passages](pdf-synthesis.md) is now implemented; [optional PDF-aware interview questions](participant-pdf-ai.md) are now implemented with separate per-upload participant permission. Ordinary text follow-ups use the written answer. The optional PDF path sends bounded extracted page text plus the current answer/description only with the separately saved permission. PDF-related provider calls occur through explicit researcher synthesis requests or the separately permitted participant interview path.

Individual PDF erasure revokes byte access, removes its description and complete review, extraction and passage-verification history, and preserves the written answer with a deletion marker. Whole-response deletion and retention also remove PDF files/reviews through the retryable deletion queue. Deleting a related image-generated question preserves and rebinds a later PDF draft to the updated turn version; PDF reviews and text/verification tied to the erased image-question context are reset while their PDFs remain available. Downloaded or already-fetched copies cannot be recalled.

Verification includes static preparation/action removal, deterministic bytes, invalid/oversized/encrypted/form/page-limit rejection, admission/consent gates, exact retries and answer binding, private headers and access scopes, review history/concurrent edits, participant non-disclosure, individual/whole-source cleanup, and mixed image/PDF lifecycle. Chromium checks mobile EN/ES/FR sharing, a lost upload response, reload, actual rendered page pixels/navigation, inert embedded actions, answer attachment, review history and deletion. Hosted checks verify the traced parser/dependencies, deployed viewer asset, private Blob lifecycle and no AI usage, with disposable sources and preservation of existing owners and the paused pilot.
