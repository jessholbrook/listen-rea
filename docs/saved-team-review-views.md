# Saved team review views

Open **Research library → Review inbox**, choose **Review requests**, **Team workload** or **Review activity history**, then use **Saved review views**. Private and workspace-shared presets persist in the hosted database across sessions and deployments. English, Spanish and French controls are available. Presets are applied explicitly; signing in does not silently replace the current/default filters.

## Save, apply and manage

Set the desired filters and select **Save current view**. Give the preset a name and choose **Private** or **Workspace-shared**. The form captures the current filter configuration when opened and guards adjacent filters, navigation and review actions until save or cancel. Existing review-planning drafts also guard preset actions. Names and search text are saved filter metadata; shared presets expose those values to the whole workspace.

Choose a preset for the current screen and select **Apply saved view**. The app fetches its current authorized version before restoring filters, then refreshes live results. It does not copy saved search results or approve/reassign any research. Normal current-source validation still runs when the underlying inbox/history is refreshed and may invalidate or erase stale dependent research under existing rules.

**Update from current filters** replaces a manageable preset's name, visibility and filter configuration with the currently shown view. **Save private copy** copies a readable preset into the current user's private list, leaving the original unchanged. **Delete saved view** removes only the preset; current filters, studies, packets, requests and activity remain unchanged. Updating or deleting requires the current version. A stale/deleted/newly private preset fails without applying new values, clears the stale catalog and requires a refresh. Failed actions never retry automatically. Success notices from earlier actions are cleared when a new preset action starts.

## What is saved

- **Review requests:** collection ID, reviewer ID or the `mine`/`unassigned` token, decision/status filters, title search and due-date window.
- **Team workload:** collection ID, title search, all/pending/overdue workload filter and the explicitly selected reviewer, if any.
- **Review activity:** packet ID, person ID or system token, action and absolute from/through calendar dates.

Pagination, language, browser time zone, open packet editors, batch selections, transfer targets, comments, approval attestations and research results are excluded. Applying resets pagination. `mine` means the viewer's own requests, including when a shared preset was created by someone else. Relative due-date windows use the viewer's current local calendar day; saved activity dates stay absolute and use the current viewer's browser time zone, matching the existing history screen.

Unavailable collection, packet or person IDs remain exact filters. They show unavailable/empty scopes rather than silently broadening the selection. Missing or foreign UUIDs in a filter never grant access: the underlying queries remain authenticated and workspace-scoped. Source deletion removes the original research/review/history under existing rules while leaving the content-free filter reference available for explicit maintenance. User-authored preset names and search strings remain until edited or deleted; they are not automatically scrubbed when research is removed.

## Visibility, ownership and limits

Any authenticated member, including a reader, can create/manage their own private presets and copy a readable shared preset privately. Private presets are visible only to their owner through the app; workspace admins cannot list, read, modify or delete another member's private preset.

Current editors can create workspace-shared presets. Every member in that workspace can read/apply them. Their creator can manage them while retaining edit access; admins can update or delete other members' shared presets. Only the creator can change visibility. An admin who wants a private variant of someone else's shared preset must save a private copy. Other editors/readers cannot modify a shared preset they do not own. Ownership is assigned by the server and cannot be changed through input fields.

Role and workspace membership are checked again in the preset transaction. A member who loses edit access can keep managing their private presets but cannot manage shared presets. When an owner leaves the workspace, their private presets are pruned on subsequent preset access. Shared presets stay with the workspace, mask the departed creator's display name and remain manageable by admins. Display names are resolved from current workspace members, never stored as copies in preset records.

Limits are **25 private presets per user** and **50 shared presets per workspace**, across all three view types. Existing presets remain editable/deletable at capacity. Changing visibility checks the destination limit. Workspace cleanup removes all owned preset records. There is no public sharing link, notification, provider call, new service, environment variable or domain/email requirement.

## API and validation

`library/saved-review-views` supports authenticated GET/POST; `library/saved-review-views/:id` supports GET/PUT/DELETE. GET detail can require `?version=N`. Inputs strictly validate visibility, name bounds, each view's exact filter fields, real/ordered activity dates and enums. Unsupported modes, action payloads, authority fields, pagination/time-zone fields, unknown or duplicate query parameters are rejected. Read responses include only authorized presets, current creator names and management flags. Private records remain private even if another actor knows their ID or cached a formerly shared version.
