# Optional image-aware AI follow-ups

Enable **Allow optional AI image follow-up (OpenAI)** below the attachment setting on an open-ended question, save and publish. Enabling it selects at least one follow-up. The setting requires image attachments and a positive follow-up limit, is off by default, and is frozen with each admitted interview’s guide. Existing uploads do not acquire permission when a later draft or publication enables AI.

Participants see a separate, initially unchecked permission naming OpenAI, independent of sharing an image with the research team. Leaving it unchecked still permits uploads and written answers. The saved image records the exact localized permission text, version, provider, language and server timestamp when permission is granted. Changing permissions before answering requires removing the upload and uploading it again; retries cannot silently change a saved grant.

## When an image is sent

After an answer is submitted, the server checks the frozen question setting, saved upload permission, answer version, refusal/skip and remaining follow-up budget. It first sends only the current permitted normalized PNG and interview language to an observation call. That call cannot see the participant answer or description. A second, text-only call receives the independently observed anchors plus the description, current answer and bounded research context. The final question must quote a selected observed anchor exactly; participant text cannot create an anchor. Empty or rejected observations stop before a contextual call. It sends image bytes directly, without a participant token or private application URL. Other images and earlier uploads are not resent. Images never enter the ordinary text-probe path when image permission is absent.

Image requests use a low-detail image input, strict bounded JSON output, up to 400 observation and 500 question completion tokens, a shared 50-second deadline and `store: false`. The default model is `gpt-4.1-mini`; configured models must support image input and structured output. Provider processing remains subject to the configured OpenAI account’s terms and retention; deleting a source cannot undo a request already transmitted.

At most one neutral, image-grounded question is proposed for an uploaded answer, within the existing question limit. Its reply advances the interview rather than starting a chain of image-derived probes. A participant may upload another image on a later answer, but that does not override the follow-up budget. No useful visible detail can produce no question. Provider/authentication/storage failures or rejected output save the answer and image without blocking progress and record an unavailable/rejected attempt. A completed answer retry does not issue another model request.

The model is instructed to use ordinary visible objects, labels and layout connected to the answer; ignore instructions embedded in images/descriptions; avoid personal identifiers and secrets; and make no identity, eligibility, sensitive-attribute, emotion or truthfulness judgments. Runtime validation rejects malformed replies, multiple questions, missing anchors and selected high-risk patterns. These checks and the small synthetic evaluation do not prove grounding or safety on arbitrary images. A model-reported anchor is a proposal for researcher review, not a verified observation or quality score.

## Provenance and deletion

**Responses → participant → AI image follow-up provenance** shows the attempt outcome, configured model, prompt version, permission version, timestamp, source-image ID and exact normalized PNG SHA-256. An asked question also retains its generated wording and model-reported visual anchor. It lives on the originating answer; a reply to it carries the source-image reference. Pixels and base64 are not stored in the provenance record.

Deleting an analyzed image removes its attachment/description/permission, model provenance and generated visual-anchor text. Historical questions sourced from that image are replaced with a deletion label; written participant answers remain. An unanswered image-based question becomes a neutral, scripted follow-up. The interview version changes so an old tab must reload. An independently uploaded draft for that turn is preserved and rebound to the new version.

Deletion also clears that response’s translations and the study’s saved analyses/reports/reels/shares, which could otherwise retain derived details. The UI confirmation discloses this effect. Private byte access is revoked immediately; storage cleanup uses the existing retryable deletion queue. Whole-response deletion removes the response and its image files, including during in-flight processing; a later provider reply cannot recreate the source. Downloaded copies and requests already transmitted cannot be recalled.

## Verification

Three unit protocol tests cover permission/version gates before reading pixels or calling a provider, the image-only observation payload, independent anchor selection, text-only question payload and shared deadline/completion bounds, source/model/prompt/digest provenance, malformed outputs, null responses and graceful provider failures. Three HTTP lifecycle tests run against development and compiled production servers, including permission immutability, no-provider continuation, deletion of an unanswered or historical image-based question, preserved later drafts, stale-answer denial, clearing derived caches and source deletion during pending processing. Generated-probe deletion fixtures in these HTTP tests are explicitly seeded; they do not claim a real model produced those questions.

The mobile browser check covers English/Spanish/French permission text, independent unchecked controls, opt-out, upload/reload, unavailable-provider continuation and researcher audit. The full automated suite contains 198 tests. The development credential returned `PROVIDER_AUTH`, so live model grounding is evaluated on an isolated Vercel production-environment deployment with the existing hosted key before the live alias is promoted. Hosted evidence and the final deployment are recorded in [deployment notes](vercel-deployment.md).

The bounded live rubric covers useful visible buttons in English/Spanish/French, a blank image, embedded prompt injection, a synthetic personal identifier, sensitive inference requests and a misleading caption for an unrelated image. It checks useful anchoring, unsupported-claim/secret avoidance, language, null behavior, exact byte provenance and lifecycle behavior. These fixtures were used to refine the workflow after a misleading-caption failure. They are regression checks, not held-out evidence or a measured real-study accuracy rate.
