# Batch recording intake

Research Library → Recording transcription → Batch recording intake adds 2–10 interviews to one study. Choose files, edit each interview title/external ID, confirm permission, then save and upload. Select a saved batch to inspect per-interview upload/transcription progress. Generate remaining transcripts explicitly; review and approve each interview individually through the existing recording editor. Drafts never enter search, analysis or briefs.

## Processing and recovery

- Uploads use the same immutable private 3 MiB parts, SHA-256 manifest, decoded duration checks and original-file storage as individual imports. Each file is limited to 60 MiB/60 minutes; the workspace still permits at most 20 pending recordings.
- One file or five-minute transcription interval runs at a time in the open browser. Pause finishes the current upload part or transcription interval, preserves its checkpoint, and starts no further work. A refresh/closed page stops browser-driven processing; this feature does not introduce a background worker.
- Saved batches derive their membership and progress from the recording records. They survive refresh and deployment. File bytes remain private; browser File objects are never persisted in local storage. Within the same page, resume pending batch uploads with the existing file selections. After a refresh, open each pending interview and reselect the same file; the server verifies its complete digest and skips committed parts.
- A failed upload or provider step preserves saved work and does not retry itself. Other interviews can continue. Refresh progress, then explicitly resume/retry. A running transcription lease remains subject to the existing two-minute recovery gate. Provider limits can require a later explicit retry; no throughput guarantee is made.
- Transcription has a separate button, can incur provider charges and sends extracted audio only to OpenAI. Creating or uploading a batch makes no provider call. Completed machine drafts still require saved researcher review and explicit per-interview import; there is no bulk approval.

## API, scope and lifecycle

`POST /api/library/recordings/batch` accepts strict JSON: batch `requestId`, `studyId`, `language` (en/es/fr), `permissionConfirmed:true`, `transcriptionPermission:true`, and 2–10 `items`, each with a unique `requestId`, title (3–160 characters) and distinct external ID (1–100). Editors only; study/workspace checks precede creation. The transaction allocates all recording stages or none, including the shared pending-capacity check. Concurrent identical requests reuse exactly the same stages; changed settings, partial/missing membership or a deleted member yield 409.

The existing recording list adds `batchId`, saved upload/transcription counts and the processing failure flag. It contains no unfinished machine text or private storage keys. All subsequent upload/transcription/review/import/delete operations reuse the individual authenticated, versioned routes; batch membership is server-owned. Callers cannot add it through the strict single-recording schema.

Membership is a content-free UUID on each recording, carried forward to its content-free import receipt. There is no separate batch document retaining titles, filenames, transcripts or removed sources. Deleting/expiring a pending recording or erasing an imported response removes that item from the group and records a workspace-scoped content-free batch tombstone, blocking stale batch-creation replay. Tombstones expire after 90 days, matching individual recording request tombstones. Existing media deletion, retention, derived-evidence invalidation and workspace isolation apply unchanged.
