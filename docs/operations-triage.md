# Operations triage

Open **Research library → Action center → Operations triage**. Current editors can select up to 25 follow-ups, preview changes to assignment and calendar due dates, explicitly acknowledge the changes and apply them. English, Spanish and French controls are available. Readers retain the action center’s read-only access and do not see triage controls.

Use the existing collection, assignee, status, date and title filters to find tasks. Triage selections persist across filters and its 20-row pages. The selected list shows every selected task and reports selections outside the current filters. Reaching 25 disables unchecked task boxes. Clearing selection leaves the proposed field settings in place; closing or cancelling refreshes the action center without applying changes.

Assignment and due date each independently support **keep**, **set** or **clear**. At least one field must request a change. Setting an assignee requires a current workspace member (the same rule as individual task editing); clearing removes the assignment. Setting a date requires a real calendar date from 2000 through 2100; clearing removes the date. Task titles, status, completion timestamps, source links, IDs and creation metadata are preserved, including for selected completed tasks. No task is completed or reopened by triage.

Preview shows current and proposed assignment/date, task status and collection for each available current-version task. Preview does not change task fields or create batch records. Applying requires explicit acknowledgement and submits only ready rows. Each task runs in its own transaction and returns applied, unchanged, conflict, unavailable, forbidden or uncertain. Rows that were already unavailable/conflicting/unchanged in preview stay in their original selection positions in final results. A row already matching the requested values does not increment its version or invalidate handoff approval. A changed version conflicts even if some fields now happen to match. Old-version replays cannot apply again. Separate overlapping batches serialize at each task version.

Task changes follow the original handoff signature rules: the collection’s handoff reviewers and final export approval become stale, even if that task was not selected into the packet. Triage immediately validates that current handoff context after each successful task change. Existing comments remain, while current-content reviewer decisions and final approval require review again. Approved research findings are not automatically changed or approved by triage. The preview explains this consequence before acknowledgement.

Current caller membership and edit role are checked during initial validation, every task transaction and final projection. Assignee membership is checked initially and again for each task. Invalid global settings or missing acknowledgement fail before task writes. Removed, foreign or source-invalid targets return unavailable without content. Current source validation and dependency cleanup follow the original collection-task and handoff workflows; deleting a source, collection or task cannot be reversed through an old batch. The final projection removes rows whose task was erased while validating another selected target.

Language and refresh controls are guarded while there are selections or proposed changes. Filters remain usable during selection and lock during preview, requests and results. Individual editors and research drill-downs are replaced by triage while it is open. Cancel and finish reload the original queue with its filters intact. If a request fails or its response is lost, the UI clears the preview, disables further application and requires finish/refresh to inspect the actual tasks. It never automatically retries a write. Successfully committed rows remain saved if a later row fails; this is not an atomic all-or-nothing batch, and no bulk undo or background continuation is provided.

`POST library/operations-triage/preview` accepts strict `{changes,tasks}` input. `POST library/operations-triage/apply` also requires `acknowledged:true`. Each target contains only task ID, collection ID and expected positive version. Duplicate task IDs, more than 25 targets, invalid dates, both fields set to keep, unsupported modes, query parameters, content/status/authority fields and missing acknowledgement are rejected. Responses project coordination values only, never research excerpts or original creation hashes. A preview is not a permission grant; apply independently validates every target again.

No new service, environment variable, provider call, email/domain setup, stored batch, research copy or migration is introduced. Validation covers strict schemas, no-op/read stability, independent outcomes, current role/workspace/assignee checks, concurrency, replay, completion preservation, handoff review invalidation and source erasure. Mobile browser checks include all three languages, cross-filter/page selection, the cap, previews/cancel, acknowledgement, partial conflicts, clear values, a response dropped after server commit, reader gates and erasure.
