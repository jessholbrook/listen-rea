# Batch review planning

Open **Research library → Review inbox → Batch review planning**. Admins, researchers and collaborators can apply a reusable workspace review plan to up to 10 saved packets in one workflow. English, Spanish and French controls are available. Readers have no batch controls. Create a reusable plan inside a saved packet's internal review first.

## Selection, preview and results

Choose a plan and start date, then select packets. Collection and title filters narrow the available packets; the selection stays explicit in a separate list when a filter or page hides a selected packet. Remove individual selections or clear the whole selection. Lists use 20-row pages, ordered by packet title and ID. A batch contains no more than 10 different packets from different collections. The initial start date uses the browser's local calendar day.

**Preview batch** prepares each original packet generation from current research and coordination state. The preview shows the shared proposed reviewer group and concrete deadlines, each packet's current reviewer list, dates and decisions, its open-comment count, and whether final approval will be reset. Calendar arithmetic and bounds match reusable review plans, including leap years and daylight-saving dates. Previewing makes no assignment changes; normal stale-source validation may invalidate or erase dependent research as it does in the original editor.

Applying requires explicit acknowledgement. **Apply to ready packets** replaces requested reviewers and deadlines, clears all reviewer decisions and final packet approval, and keeps existing comments and resolution state. It uses the same dependency capture and mutation rules as individual packet review. Open comments still block review approval. Final export still requires every requested person's own current decision, resolved comments, eligible research and explicit final approval.

Packets commit independently in selection order. A stale packet can report a conflict while another applies successfully; a deleted or replacement generation is unavailable. Successful packets are not rolled back when a later packet conflicts. Results show applied, changed, unavailable, forbidden or uncertain outcomes for every selected packet. Rows already unavailable during preview remain in their original positions after applying the ready packets. Conflict titles are read from the current workspace record; deleted or inaccessible packets do not receive old titles, reviewer lists or comment details. Final existence checks remove projections erased while validating another packet with shared sources.

Cancel returns to a refreshed inbox without applying requests. Finish also refreshes the inbox and clears the selection. While selecting, preparing, confirming or inspecting results, adjacent mode/language/refresh controls are guarded. Selection can be cleared before preview to leave the workflow. A changed/deleted template or failed request clears the preparation until refresh. No failed packet or interrupted request retries automatically. If a request is interrupted, some packets may already have committed: inspect the refreshed originals before starting a new preview. Replaying old packet versions reports conflicts rather than resetting successful reviews twice.

## Server rules and lifecycle

Authenticated editor-only POST endpoints are `library/review-plan-batch/preview` and `library/review-plan-batch/apply`. Inputs are strict, bounded and reject duplicate packet or collection IDs. Preview requires the plan ID/version, start date and original packet/collection IDs. Apply additionally requires each prepared packet version, review version and content signature, plus acknowledgement. The server derives reviewers and dates from the saved plan rather than accepting copied assignments or client-computed deadlines.

Template availability/version, calendar validity and reviewer membership are checked before processing. Each write rechecks the original packet generation and current content/review versions transactionally. The caller's workspace/edit role is checked again before each packet preparation and mutation. The saved template version and reviewer availability are checked for every mutation. A template or membership change during a batch can therefore leave earlier successful packets applied and later packets in conflict. Stale-source cleanup commits separately before a rejected write so rejection cannot resurrect erased research.

Preview and result responses contain coordination metadata only: identities, titles, reviewer display names/dates/current decision timestamps, open-comment counts, approval flags and optimistic version/signature fields. They contain no summaries, findings, transcript passages, comment bodies, email addresses, provider output or internal comment history. Unexpected per-packet errors return an uncertain outcome without exposing exception details. A global request failure after earlier commits is handled by the same refresh-and-inspect workflow.

No batch documents, copied packet research, background jobs, provider calls or email notifications are created. Applied requests live only in the owning packet's existing feedback record. Source/packet/collection deletion erases that review under existing dependency rules; reusable coordination-only templates remain until explicitly deleted. Workspace cleanup removes templates and feedback. Domain-dependent email remains deferred.
