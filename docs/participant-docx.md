# Private DOCX uploads and researcher review

Enable **Allow optional participant DOCX attachment** on an open question. The setting follows saved drafts, published revisions and frozen participant sessions. Participants may answer without a file. Uploading requires an unchecked, explicit sharing checkbox and a 3–500 character description. English, Spanish and French controls explain that only a prepared body-text snapshot is shared, the original file is not retained, and this step sends no document text to AI.

The participant can inspect or download prepared text before submitting, reload or remove the draft, and attach it to the exact answer/version. A selected local file alone is not shared. Lost upload acknowledgements can be retried with the same request ID/file/description; a reused ID cannot replace different bytes or a deleted draft. Each answer has at most one DOCX; separate image/PDF attachments can coexist. There are at most 20 DOCX attachments per interview.

## Preparation and viewing

DOCX files up to 3 MiB are prepared in a separate Node process with PATH/NODE_ENV only, a 96 MiB V8 old-space cap, eight-second deadline and bounded output. The process opens no extracted files and fetches no relationships, links or external entities. It accepts a bounded OOXML Word package, reads content types/root relationships/main body, and validates ZIP header consistency and CRCs for consumed XML parts. Encrypted/macro-enabled files and malformed packages are rejected. Limits are 300 ZIP entries, 2 MiB per declared entry, 10 MiB total declared expansion, 64 XML levels, 50,000 XML elements, 2,000 body paragraphs and 200,000 text characters. ZIP streams and output are bounded independently; DOCTYPE/processing instructions and external entities are rejected. These are not an OS sandbox or a total native-memory guarantee.

Only visible body paragraph text is retained, in document order, including text in table cells and displayed inserted text. Hyperlink labels become plain text; targets, images, objects/text boxes, formatting, headers/footers, footnotes/endnotes, comments, properties and deleted/moved-from text are omitted. Inline explicit hidden runs/paragraphs are omitted. Documents defining hidden styles are rejected because this first extractor does not resolve style inheritance. It does not reproduce Word layout or page numbers, OCR images, evaluate fields or compare tracked-change versions. Preparation may omit context; a researcher must review the snapshot's limits.

Private storage contains only a validated `{version:1,paragraphs:string[]}` JSON snapshot. Original bytes/filenames/author metadata are not stored; the original-byte SHA-256 binds retries/review provenance. Browser viewing renders escaped plain text, without HTML, iframe or Office rendering, under authorized no-store JSON access with nosniff/sandbox headers. Downloads are clearly labeled prepared `.txt` files. Paragraph references are one-based positions in this prepared snapshot, not original Word paragraph IDs or page numbers.

## Researcher review and erasure

The response transcript and library show private DOCX text. After the file is submitted with its answer, researchers can save quality flags and notes with reviewer/time and immutable revision history. Reviews bind to the current file digest, answer, question, attachment, interview and turn. Updates require edit authority and exact source/version; stale or concurrent writes are rejected. The cap is 50 review revisions, with notes up to 2,000 characters. Read-only members can inspect permitted workspace content but cannot write reviews or delete files.

Quality review records and full body snapshots stay out of shared reports and external API/MCP DTOs. Ordinary written-answer moderation does not receive DOCX text. [Optional document-aware follow-ups](participant-docx-ai.md) use bounded prepared paragraphs only with a frozen guide setting and separate per-upload participant permission. Separately [verified and explicitly included selections](docx-evidence.md) can appear in report appendices with reviewer attribution and reach researcher AI through [explicit DOCX synthesis](docx-synthesis.md) or [passage Q&A](docx-qa.md). Participant-token access is limited to the participant's own document; review endpoints are workspace-only. Review notes stay internal and are not independently verified document facts or participant statements. The original written answer stays separate.

Participants can remove drafts; only researchers can delete submitted files. Deletion removes prepared text, metadata/description and review history, revokes saved study analyses/editions/share links and preserves written answers. Whole-response retention/purge removes DOCX storage and reviews through the existing deletion queue. Related image/PDF question redaction keeps outstanding DOCX draft versions coherent and clears DOCX reviews bound to removed prompt context. Tombstones prevent retry resurrection of deleted uploads.
