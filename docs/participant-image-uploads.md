# Participant image uploads

Researchers can enable **Allow optional participant image attachment** on an open-ended question, then save and publish. Participants can attach one image to each answer on that question, including a follow-up answer, or continue without an image. The published setting is frozen with each interview’s guide; drafts and later publications do not change admitted sessions. Researcher previews use their saved draft and remain separate from real responses.

## Participant flow and limits

Choose a PNG, JPEG or WebP file up to 2 MB, add a description of 3–500 characters, and explicitly agree to share it with the study team. Sharing starts when **Upload image** is selected. A file selected in the browser is not uploaded automatically. The interface reminds participants to remove personal details and share only images they have permission to use.

The server validates the declared format against decoded content, bounds input to 16 million pixels, applies orientation, resizes to fit within 1,600 × 1,600 without enlargement, and writes a static PNG of at most 3 MB. EXIF and other source metadata are stripped; the original filename and original file are not saved. This does not remove personal details visible in the image. Description text is saved as supplied, with whitespace trimmed; it is not automatically translated.

An uploaded draft survives reloads. The participant can view it at full size, remove it or replace it before submitting an answer. It attaches to that exact answer when submitted. An uploaded image cannot be silently omitted from the answer request: submit it or remove it first. Uploads are unavailable until any timed/video presentation gate allows answering. Each interview permits up to 100 stored image attachments; uploads are rate limited. Unsubmitted uploads remain part of the interview’s private data and follow existing retention/source-deletion rules.

Retries reuse an immutable ID scoped to the interview, answer version and client upload attempt. Exact bytes and description recover the existing upload. A different image/description needs a new attempt. Submitted images cannot be reused on another turn or interview. If a request times out, reload to see a saved draft or retry the same file. The browser check simulates a successful upload with a lost response and verifies this recovery.

## Researcher access and deletion

Open **Responses → participant** to view the image beside its answer, description and upload time. Included completed sources also show their attachments in the Research Library. Image bytes require the owning participant token or authenticated access to the study’s workspace; IDs do not create public links. Responses are private, uncached and marked `nosniff`. API/MCP read projections and report exports do not gain image downloads in this stage.

**Delete attached image** removes the private file, saved description and attachment metadata, while preserving the written answer and a deletion timestamp. This action also refreshes the study’s data version. Participants can remove their unsubmitted draft; the research team handles deletion after submission. Removing an entire response, including through retention, deletes its attached and draft files through the existing durable cleanup queue. Access is revoked when metadata is removed, with failed storage deletions retained for retry. Content-free tombstones prevent deleted upload attempts from being adopted by a later retry.

## Validation and scope

Four HTTP lifecycle tests run against development and compiled production servers: normalization/metadata stripping, access isolation, exact retries, answer binding, draft recovery/replacement, individual/source deletion, deletion-versus-answer races, malformed/oversized uploads, missing permission/version, unsupported question types, timed gates, publication snapshots, previews, optional opt-out and English/Spanish/French descriptions. The mobile browser check covers editor setup, explicit sharing, upload/reload/removal, lost-response retry, answer attachment and researcher erasure in English/Spanish/French. Hosted synthetic evidence is recorded in [deployment notes](vercel-deployment.md).

The base attachment flow does not send image pixels to AI. [Optional image-aware AI follow-ups](participant-image-ai.md) are now available only with the published question setting and separate upload permission. Attachments do not verify identity, ownership or eligibility and do not add an automated response-quality score. PDFs, documents, arbitrary file types and file-aware AI analysis remain separate. No real participant was contacted or asked to upload data during implementation.
