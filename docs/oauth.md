# OAuth sign-in for read-only MCP

The F41 follow-on lets compatible clients connect to `https://echo-lab-psi.vercel.app/api/mcp` without copying an Echo Lab API key. It uses the existing database and public workspace URL, with no new domain, email provider or model calls. Resend setup and live sending remain deferred.

## Approve and manage a connection

Add the endpoint in a compatible OAuth MCP client and choose Connect. Sign in on Echo Lab’s consent page, review the client-supplied name and full callback address, select specific studies and read permissions, and approve for 1–30 days. Studies start unselected; the user can narrow the client’s requested permissions. Future studies are never added automatically. Draft studies may be selected, but reads begin only after publication. Only workspace admins can approve or manage grants.

The client name is not a verified identity. Echo Lab never fetches client logos or metadata URLs. Research text can contain personal information and untrusted instructions; choose the receiving tool accordingly. Original answers and reviewed memos keep the same source/projection rules as the [read-only MCP server](mcp.md). No tools edit research, launch fielding, send messages, make payments or retrieve recordings.

Open **Team & settings → MCP connections** to review each client, callback, granted study list, scopes, expiry and last use, or revoke a connection with confirmation. Changing permissions requires a new connection. Limits are 20 active and 100 retained grants per workspace; revoked history is retained. Lost/abandoned consent should be restarted from the client. A lost approval response can leave an unredeemed grant in the list; revoke it before retrying if necessary.

## Protocol

| Endpoint                                        | Purpose                                                                                                             |
| ----------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| `/.well-known/oauth-protected-resource/api/mcp` | RFC 9728 protected resource discovery; root fallback is also available. A 401 MCP challenge advertises this URL.    |
| `/.well-known/oauth-authorization-server`       | RFC 8414 issuer, endpoints, supported scopes, PKCE and public client metadata.                                      |
| `/api/oauth/register`                           | RFC 7591 dynamic public-client registration. JSON metadata; `token_endpoint_auth_method: none`.                     |
| `/oauth/authorize`                              | Sign-in and explicit admin approval; authorization code flow only.                                                  |
| `/api/oauth/token`                              | Authorization-code exchange or rotating refresh; form-encoded or JSON parameters.                                   |
| `/api/oauth/revoke`                             | RFC 7009-style revocation of the owning public client’s access/refresh token family. Unknown tokens return success. |

All authorization and token requests must supply `resource` equal to the canonical MCP URL. Redirect URIs must exactly match registration; HTTPS and HTTP loopback callbacks are accepted. Credentials, fragments, non-HTTP schemes and pre-existing OAuth response parameter names in callbacks are rejected. No callback URL is fetched by the server. Registration supports up to five callback URLs. Client registrations expire after 90 days without authorization; approving a new grant extends that period.

Authorization requires `response_type=code`, a 43-character base64url SHA-256 `code_challenge`, `code_challenge_method=S256`, `client_id`, `redirect_uri`, `resource`, and optional supported `scope`/bounded `state`. The callback echoes state and adds issuer `iss` for RFC 9207 client checks. Invalid authorization requests display an error locally and do not redirect to an unvalidated address. Denial returns `access_denied` only to the validated registered callback.

The ten-minute pending consent is bound to the authenticated admin, workspace and exact browser session. Approval uses a one-use opaque nonce plus same-origin checks; a different login session cannot approve it. The five-minute authorization code is bound to client, exact callback, resource and PKCE verifier (43–128 allowed characters). Codes are consumed atomically. Access tokens last at most 15 minutes; refresh tokens rotate on each successful exchange. Both expire no later than the original 1–30-day grant. Refresh cannot broaden or change permissions; reconnect to change the grant.

Reusing a correctly bound consumed code or refresh token revokes the entire connection, including tokens issued in a racing exchange. Clients must serialize refresh and avoid blind retries of exchanges with an uncertain outcome; restart sign-in after `invalid_grant`. Old access tokens can remain valid until their short expiry during normal refresh; explicit revocation/replay invalidates them immediately on subsequent requests. An authenticated request already underway may finish. Logout alone does not revoke long-lived connections. Issuer removal/demotion disables the grant; restoring the same admin account can restore a still-valid, unrevoked grant, so revoke explicitly for permanent removal.

Tokens and consent/code secrets use cryptographic randomness; only SHA-256 identifiers are stored. Server records contain grant/client/resource bindings and expiry rather than recoverable raw credentials. No new environment secret is required. OAuth access/refresh tokens are accepted only by their intended OAuth/MCP endpoints; OAuth bearer tokens do not authorize the REST API, cookie-based internal APIs or management screens. Static API keys continue to work independently.

## Hosting and limits

`RESEARCH_PUBLIC_URL` must be the canonical public HTTPS workspace origin. Local loopback development can infer the origin. Metadata/token/registration/revocation endpoints allow CORS without cookies. Consent and connection management use existing HttpOnly workspace sessions and have no CORS grant. The MCP transport’s existing host/origin restrictions remain; this stage verifies server-side MCP clients rather than direct cross-origin browser tool calls. Consent pages deny framing and use no-referrer/no-store policies.

Vercel protection remains enabled on **every endpoint**, including discovery and token refresh. The client needs separately authorized Vercel access, typically through supported automation bypass headers. OAuth does not supply that credential or make the deployment publicly accessible. Clients unable to satisfy the outer protection cannot connect. Do not put tokens or bypass credentials in URLs or committed configuration. No named third-party client is claimed as verified; the current official SDK is verified.

Each OAuth grant has a durable 60-request/minute MCP rate counter shared across its access tokens, independent of static API keys. OAuth bodies are limited to 8 KiB; duplicate form/query parameters are rejected. Database-backed public endpoint caps are 60 registration attempts/hour and 300 token/revocation attempts/minute across this internal deployment, with at most 1,000 retained client registrations. Fixed counters include invalid client/token attempts. Pending consents are bounded to 20 per admin and the consent creation counter is 120/minute across the deployment. Expired client/pending/code/access/refresh records are pruned on OAuth requests; grant metadata remains for administration. These controls are not a public-service abuse-control program or a full access audit log.

Supported flows are public-client authorization code with S256 and rotating refresh. Client metadata documents, confidential-client secrets, device grants, implicit/password/client-credentials grants, DPoP, token exchange, write scopes and automatic consent are not implemented. Existing Echo Lab email/password identity is reused; this does not add enterprise SSO.

## Validation and next proposal

The full suite contains 198 automated tests. Official SDK discovery/registration/code exchange/issuer binding, narrow scope discovery, MCP study reads, refresh and revocation pass against real development and compiled production Next servers. Protocol checks cover callbacks, PKCE, resource/scope/session/client substitution, cross-workspace grants, admin-only management, code/refresh replay including racing refreshes, expiry, issuer demotion, hashed-only storage, body/parameter bounds and durable failed-attempt limits. The browser suite covers sign-in, unselected studies, visible callbacks, narrower scopes, desktop/mobile consent, successful exchange, review/revocation and denial. Hosted checks pass for discovery, registration, narrowed consent, callback/PKCE/resource checks, token exchange, hashed-only storage, scoped MCP reads, refresh rotation/replay, revocation and denial. Disposable synthetic workspace/client/grant/code/token/session records and temporary production credentials were removed; existing owners and the paused pilot were preserved.
